STRUCTURAL FIX (launch_wave setup only, additive, fail-open): in `setup_wave` (mu/tools/executors/launch_wave.py), AFTER the worktree + bridge_config setup (setup_routing_record / ensure_bridge_config_path + sync_bridge_config_agents_from_defaults), add a `_prestage_l4_indicator(repo_root, config)` helper that, WHEN the WaveConfig declares a non-empty `indicator_collection_command` AND `indicator_artifact_ref`, RUNS the indicator_collection_command (cwd=repo_root) and `git add`s the indicator_artifact_ref path, so the L4 `--staged` contract finds the indicator PRESENT at Phase-B review. STRICTLY BEST-EFFORT / FAIL-OPEN: any failure (command error, missing artifact, git-add failure) logs a WARNING and RETURNS WITHOUT RAISING -- it must NEVER break or abort a wave launch (commit_executor Step 5 remains the authority and idempotently regenerates+stages the indicator at commit, so a failed pre-stage is harmless). Do NOT change any gate semantics, the consistency-check, or commit Step 5; only pre-generate the artifact at launch. Wire the helper into the launch path so it runs on `--launch` (and is a no-op when the wave declares no indicator). Add regressions in the launch_wave test module (create test_launch_wave.py if absent): (a) a config with an indicator_collection_command -> after setup the indicator artifact exists on disk AND is staged in the index; (b) a config whose indicator_collection_command exits non-zero -> setup still SUCCEEDS (fail-open) and logs a warning, launch not aborted; (c) a config with empty indicator fields -> no-op. Name the helper exactly `_prestage_l4_indicator`. No host semantics.
